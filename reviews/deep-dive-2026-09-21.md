# DeepSwing: learning-system review

Reviewed 2026-09-21. Scope: the local source checkout, with emphasis on whether simulated experience can produce demonstrably better trading instructions.

## Assessment

The architecture has the right major pieces: recorded model inputs, deterministic execution checks, separate model tracks, feedback on skipped opportunities, reusable rules, compiled prompt versions, and offline replay. The main weakness is the reliability of the experiment connecting these pieces. Several defects can change which outcomes are considered good, leak later information into validation, or make a failed evaluation look like a cautious model.

I would repair measurement and validation before spending more on prompt optimization. Otherwise MIPRO can successfully optimize a score that does not represent executable, net trading outcomes.

This review distinguishes reproduced behavior from code-traced findings and proposed experimental improvements. It does not establish the performance of the deployed system: this checkout contains no production database, learned rules, or compiled programs, and the external FinanceData implementation was not inspected.

## Highest-priority findings

### 1. The optimization metric cannot evaluate proposed stops and targets

**Evidence:** `src/portfolio/metrics.py:203`, `src/scheduler/optimizer.py:71`, `src/agent/replay.py:346`.

`decision_metric` reads only the predicted action and the example's existing R-multiple. A replay adapter also discards every output except the action. Consequently a valid BUY, a BUY with its stop above entry, and a BUY with non-finite levels receive exactly the same score for a given example. The isolated reproduction gave all three **0.85195** on a +2.5R example.

This is a mismatch with `TradeDecision`, whose instructions explicitly ask the optimizer to produce structural stops and targets. It also means a previously blocked BUY can be rewarded without fixing the reason execution rejected it. Real-trade labels inherit the previous prompt's exit plan, while counterfactual labels use a fixed ATR/minimum-RRR plan.

**Improve:** make an explicit scope choice. For an entry-selection experiment, hold execution policy fixed and optimize BUY/PASS alone. For a complete trade-plan experiment, validate each predicted stop/target and simulate that actual plan over a stored forward path, including net costs. Keep invalid predictions and operational failures separate from intentional PASS decisions. Report selection quality and execution validity separately even when using a combined objective.

**Acceptance:** changing only the predicted stop or target must change the score when it changes validity or the realized path; alternatively, those outputs must be removed from the program being optimized.

### 2. Counterfactual labels do not share the live execution semantics

**Evidence:** `src/scheduler/optimizer.py:83`, compared with `src/portfolio/simulator.py:520` and `src/backtesting/engine.py:200`.

The labeler fills stops at the stop level even when a bar opens below it, omits trailing stops, and computes gross price movement rather than net proceeds. It uses the default commission setting for its breakeven threshold without a market-specific FX surcharge. It also omits the decision day's remaining intraday path. These differences matter because counterfactuals can outnumber actual trades four to one.

Two reproduced examples:

- Entry 100, ATR 2, stop 97, next open 90: the labeler reports **-1R**, although a gap fill at 90 is **-3.33R before costs**.
- An armed breakeven stop produces the label **PASS with +0.08344R**. The metric therefore scores BUY at **0.51460** and the label-following "oracle" at **0.48540**. The supposed oracle is not always an upper bound on its own metric.

**Improve:** extract a shared execution-policy component used by backtesting and counterfactual labeling. Give it the policy version, market/currency, entry fill, original risk, costs, and forward bars. Derive labels from the same net utility that the evaluator uses; near-zero outcomes can be neutral. Preserve the distinction between daily-bar approximations and live polling, and quantify that difference rather than calling the two identical.

**Acceptance:** gap, trailing-stop, breakeven, both-hit-bar, cost-only-loss, and horizon-expiry fixtures agree across evaluation paths. The oracle must maximize the metric for every individual example.

### 3. The forward validation split is not reliably chronological

**Evidence:** `src/agent/replay.py:91`, `src/scheduler/optimizer.py:326`, `src/scheduler/optimizer.py:329`, `src/scheduler/optimizer.py:394`.

Counterfactual rows begin newest-first, but sampling regroups them by ticker. Reversing the resulting examples does not restore chronological order. A reproduced ten-example case put time **9 in training and time 8 in validation**.

Additionally, the two example types are split independently rather than across one global date boundary. Actual trades are accumulated by close order, which is not necessarily decision order. Finally, training labels can use forward prices that overlap a validation period even when decision timestamps are sorted correctly.

**Improve:** retain `decision_time`, `label_available_at`, `label_end_time`, ticker, and source type on each example. Use one global temporal cutoff, training only on outcomes that were available before it. Purge overlapping outcome windows at the boundary. Control source composition within those constraints rather than independently splitting source lists. Reserve a later untouched test period for promotion decisions.

**Acceptance:** assert that every training label was available before the validation boundary, and test interleaved tickers, long-held trades, and mixed real/counterfactual examples.

### 4. The replay CLI can silently evaluate model failures as PASS

**Evidence:** `scripts/replay_decisions.py:115`, `src/agent/replay.py:346`.

The baseline loader constructs `dspy.Predict(TradeDecision)` but never builds or configures an LM. The score path supplies no LM context either. In a fresh CLI process the baseline therefore has no configured model. This finding is code-traced; the real DSPy runtime was not available for an integration run. A compiled artifact may carry different model state, so its behavior should be checked independently.

The adapter catches every prediction exception and returns PASS. On a corpus dominated by losing opportunities, a broken evaluator can thus earn an apparently respectable score. Invalid action strings are also mapped to PASS.

**Improve:** add an explicit track/model option, call the existing `build_lm`, and scope calls with `dspy.context`. Pass only the declared input fields. Record errors and invalid outputs separately, run a startup smoke call, and stop an evaluation that cannot meet its completion threshold. Log model, reasoning settings, costs, and successful-call count with the result.

**Acceptance:** a fresh-process baseline smoke test succeeds with the supported SDK; deliberately missing credentials or a forced model exception fails the run instead of producing an all-PASS result.

### 5. Backtests can exit a position before its entry could have happened

**Evidence:** `src/backtesting/engine.py:425`, `src/backtesting/engine.py:464`, `src/backtesting/engine.py:471`.

The engine builds signals using the day's completed bar, opens at that day's close, then checks the new position against that same day's open/high/low. Those prices occurred before the close-price entry.

Following that sequence with a close-price entry of 100 and a stop of 97, on a bar with low 96 and close 100, immediately closes the new trade at 97 on its entry date. The probe reproduced this impossible order of events.

**Improve:** adopt an explicit event sequence. For example, compute signals after day D closes, execute at D+1 open, and then process D+1 exits. Revalidate the trade at its actual entry price. If retaining an idealized D-close fill, do not expose it to D's prior intraday range. Process existing holdings before sizing new entries so capital and equity reflect current events.

**Acceptance:** a low that occurs before entry cannot stop out the trade; a gap on the next entry bar changes the fill and risk validation.

### 6. Rule deduplication can suppress the opposite advice

**Evidence:** `src/agent/memory.py:30`, `src/agent/memory.py:39`, `src/agent/memory.py:61`.

Canonicalization removes `not`, `no`, `above`, and `below`, as well as all numbers. Both retrieval diversity and permanent supersession rely on this representation.

The reproduced pair, “RSI above 70 → Do buy the breakout” and “RSI below 70 → Do not buy the breakout,” receives **similarity 1.0**. The system can treat contradictory rules as interchangeable and remove one from circulation.

**Improve:** preserve negation and comparison direction immediately. Longer term, store a structured predicate, threshold/range, action polarity, applicability, and explanatory text. Distinguish duplicate, related, and contradictory rules. Do not automatically collapse thresholds until their equivalence has been tested.

**Acceptance:** opposite polarity or inequality direction must never qualify as duplicate; threshold variants remain inspectable and carry their own evidence.

### 7. Rule feedback mixes incompatible units and does not establish causality

**Evidence:** `src/scheduler/scan_loop.py:897`, `src/scheduler/optimizer.py:220`, `src/agent/memory.py:216`, `src/agent/memory.py:390`.

Actual trades supply `closed.pnl_pct` to `record_outcome`, while counterfactual decisions supply an R-multiple. The function multiplies either by ten and clips to ±1. For a rule used alone, a **-3% actual trade updates quality by -0.3**, while the corresponding **-1R counterfactual updates it by -1**. These are different weights for equivalent evidence.

Rules also get credit for being included in the prompt, weighted by retrieval rank, without evidence the model followed them. Retrieval ranks primarily by quality, market and regime; it does not check whether the rule's technical trigger is actually true. Core promotion requires accesses and quality, but no minimum measured-outcome count: an initially high self-rated rule can become core through exposure alone.

**Improve:** use one explicit utility unit, separate self-reported confidence from empirical performance, and require distinct outcome evidence for promotion. Record which rules were applicable and which the model cited or followed. Evaluate selected rules using paired replay with/without them on the same frozen opportunities. Treat ERL explanations from a single trade as hypotheses, not established causes.

**Acceptance:** equivalent real and simulated outcomes cause the same update; an untested rule cannot become core solely from being shown repeatedly.

### 8. Position caps can cancel the drawdown size reduction

**Evidence:** `src/agent/risk.py:177`, `src/agent/risk.py:185`.

The code halves risk-based size before applying the position-value cap. Where that cap binds both sizes, normal and drawdown modes execute the same quantity.

With 100,000 equity, entry 100 and stop 97, the reproduced normal size is **100 shares** and the drawdown size is also **100 shares**, despite the log saying it was halved.

**Improve:** apply the drawdown multiplier to the final executable size, or proportionally reduce all binding size budgets. Keep risk, cash and allocation limits enforced after adjustment.

**Acceptance:** otherwise identical valid trades under drawdown use half the final normal quantity, within rounding tolerance.

## Further correctness and measurement improvements

### 9. Reject non-finite predictions before arithmetic

`src/agent/risk.py:81` accepts both NaN and infinity as targets in an otherwise valid proposal; the probe verified both. Comparison checks against NaN do not reject it. Validate finite positive prices, ATR, equity and sizes at the model boundary and again at the execution boundary. Add finite/range checks to settings that control execution.

The cost-floor calculation at `src/agent/risk.py:125` also uses `round_trip_cost_frac`, which actually returns a **per-leg** commission rate. A setting described as three round trips is therefore applied to three single legs, excluding slippage. Rename the helper and calculate the actual round-trip cost explicitly.

### 10. Performance metrics are inconsistent across engines

`src/backtesting/engine.py:53` and `:59` report gross return and R; `:534` uses gross wins while total P&L subtracts commissions. A reproduced trade with **-3.002 net P&L** was counted as a winner with positive R. Backtest `optimization_metric` also multiplies win rate by mean R, unlike the live expectancy metric.

`src/portfolio/metrics.py:78` returns zero total return whenever no trades have closed, even if open positions have changed equity. The reproduction returned **0% for a portfolio down 10%**. Its historical drawdown series contains realized closes only. The backtester similarly discards its intraholding equity history when calculating reported drawdown. Both Sharpe calculations are based on individual, potentially overlapping trades rather than a regularly sampled portfolio return series.

**Improve:** share definitions of net P&L/R and persist timestamped portfolio NAV snapshots. Calculate portfolio return and drawdown independently of closed-trade count; calculate portfolio risk statistics from regularly spaced NAV returns. Include horizon-forced exits explicitly and report realized versus open results clearly.

### 11. Default regime classification ignores much of its stated window

`src/analysis/regime.py:83` uses prefixes `ts[:lag]`. For a 100-price input, the largest prefix is 45 prices: the latest **55 prices do not affect the estimate**. Replacing all those prices left the reproduced estimate unchanged at **0.48512**. `config/settings.py:145` keeps this estimator active by default.

The repository already has a returns-based alternative. Validate that estimator with controlled series and shadow-run it on saved opportunities before switching the candidate gate. Monitor how the change affects coverage; a stricter funnel can reduce learning data substantially. Version the regime policy in every sample.

### 12. Mechanical exits run after potentially slow model reviews

`src/scheduler/scan_loop.py:740` performs news/LLM exit reviews before `portfolio.update_prices` at `:754`. A position that has already breached its stop can wait on an unnecessary model call and be labeled `news_exit` if the model sells first. That changes ERL's explanation of the trade. The review also reuses entry-time technicals in the holdings-only path while the exit signature describes current technicals.

**Improve:** process mechanical exits first using timestamped quotes, then review remaining holdings. Explicitly label stale technical context or refresh it. Keep observed quote time separate from processing/fill time. Avoid blocking the stop sweep behind long candidate scans if that sweep is meant to have an independent cadence.

### 13. The instruction asks for market structure absent from its input

`src/agent/decision.py:18` asks for swing lows/highs, measured moves and structural invalidation. `src/analysis/technical.py:49` supplies indicator levels and two Fibonacci retracements, but no explicit swing-high/low sequence, bar history, support/resistance provenance, or distances and ages of those levels.

**Improve:** supply deterministic, timestamped structural features and identifiers the model can cite. Include ticker, currency, price timestamp, data freshness and execution constraints explicitly. Require a selected level and a reason that can be checked against those features. This makes the learned instruction more grounded and its errors easier to diagnose.

Volume selection at `src/analysis/technical.py:149` always uses the penultimate bar, assuming the last bar is incomplete. That is not true for every provider or an end-of-day historical slice. Determine bar completion from exchange time and provider metadata, and keep that policy identical in replay.

### 14. The experiment is not fully reproducible or representative

`src/db.py:49` does not retain prompt hash, model/config version, predicted levels, or the full execution decision for every decision row. Input snapshots are limited to one per track/ticker/day. Material intraday changes can therefore be lost. The replay corpus covers PASS/BLOCKED rows only, rather than all opportunities; screening, triage and funding gates further restrict what the system can learn about. Evaluating with saved heuristic text measures a new prompt under the old memory context, not the entire current learning policy.

Corpus JSON has no manifest identifying labeler, execution settings, source data or code revision. Relabeling old decisions uses current settings. The 90-day decision-retention setting can remove the original evidence needed for long-term comparisons. The two tracks share a funnel but can see different opportunities once capacity differs; sequential prompt versions also encounter different market periods.

**Improve:** create an immutable experiment record and compressed research archive separate from the operational database. Keep decision ID/time, exact inputs, raw/parsed output, quote provenance, prompt/model/config/memory versions, risk result, fills, and label availability. Freeze labeled corpora with manifests and hashes. Save a representative sample of screened-out and triaged-out opportunities for shadow evaluation. Compare programs on paired opportunities and report coverage by market, regime and source type.

## Prompt promotion and the intended end product

At `src/scheduler/optimizer.py:462`, compilation selects on its validation set, then the result is saved and reloaded immediately. There is no independent incumbent-versus-challenger promotion gate. The old artifact is renamed before the new artifact is saved, so a failed save can also leave no active file for the next restart.

The useful end product should be a versioned instruction package containing:

- The human-readable instruction and its machine-loadable program.
- Input/output schema and the execution policy it assumes.
- Learned rules with applicability, supporting observations and counterexamples.
- Training/validation/test periods and immutable corpus identifiers.
- Baseline and incumbent comparisons, error/invalid-plan rates, net R, trade coverage, and portfolio results.
- Performance breakdowns and uncertainty estimates accounting for related ticker/time observations.
- Known limitations, model/settings identity, promotion rationale, and rollback artifact.

Use MIPRO's validation set for candidate selection, a separate later test set for promotion, and paired shadow decisions for prospective confirmation. Freeze policies during a comparison. Require a meaningful advantage over the incumbent as well as trivial references, with enough distinct opportunities to support the claim. Do not interpret the numerical minimum of 30 closed trades as evidence that a prompt is validated.

Start by evaluating entry selection under one fixed execution policy. Then evaluate trade-plan generation and exit management separately. This makes it possible to attribute improvement to the instructions being changed. The current `exit_decide` creates an uncompiled program on each review, so entry optimization should not be presented as optimization of the whole trading policy.

## Suggested delivery sequence

1. **Make evaluation fail honestly:** configure replay LM context, separate errors from PASS, reject non-finite outputs, and preserve the incumbent until a candidate artifact is safely saved and validated.
2. **Repair the outcome ledger:** share net accounting/execution semantics; fix counterfactual gaps, breakeven labels and trailing behavior; fix backtest event order, drawdown sizing and contradictory-rule deduplication.
3. **Repair the experiment:** add timestamps/provenance to examples, use a purged global time split, freeze a representative corpus, and build an incumbent/challenger report with a promotion gate.
4. **Improve the learning inputs:** normalize rule feedback, test rule applicability and contribution, add structural features, and shadow-test regime and funnel changes.
5. **Produce the instruction package:** export readable instructions, supported rules and evaluation evidence together. Optimize only once that evidence can distinguish improvement from measurement artifacts.

- Traced the entry, risk, simulation, ERL, heuristic maintenance, MIPRO, replay, backtest and metric paths, plus persistence and relevant tests.
- Executed the repository's selected function/class definitions in an isolated harness with repository default settings and synthetic inputs. **Eleven assertions reproduced the behaviors described above.** This bypasses unavailable infrastructure imports; it is not an integration test or a full test-suite run.

- Existing `tests/conftest.py` injects MagicMock substitutes for SDKs and framework modules whenever they have not already been imported, even if installed. Keep fast unit mocks, but add a separate real-SDK, no-paid-call integration lane for program configuration, serialization and loading. The checked-in deployment workflow does not run tests before deployment.
- Application code and configuration were not changed. The report and reproduction harness are review artifacts only.
